## 三、逐项分析与可复现实验

### 01｜llama.cpp CUDA 低比特 MMVQ 优化

**来源/日期**：[ggml-org/llama.cpp PR #30517](https://github.com/ggml-org/llama.cpp/pull/30517)，2026-10-17 合并。**结论**：优化低比特量化的 matrix-vector 内核，效果高度依赖量化格式、微批大小和 GPU 架构；**不等于现有 IQ4_XS 自动提速**。**开发者实测**：RTX 4090 + Qwen3.5-9B Q3_K_S，tg128 从 162.65 到 174.93 tok/s（1.08×）；RTX 3090 同模型 81.04→126.22（1.56×）；GB10 + DeepSeek-V4-Flash IQ2_XXS+Q2_K 为 19.13→19.24（1.01×）。Q4_K/Q8_0 的单算子多为约 1.00×。这些不是 4070 Ti Super 测试。**适用/限制**：4070 CUDA 可测 Q2_K/Q3_K_S 与 IQ4_XS 对照；低比特可能损失质量。**复现**：固定 PR 合并前后 commit，Qwen3.5-9B Q2_K/Q3_K_S 与既有 27B IQ4_XS 分别跑 -p 256/2048 -n 128/256 -ub 1/2/4/512 -fa 1 -ngl 999 -r 3；记录 pp/tg、VRAM、正确率、功耗。**建议 P0**：先小模型 A/B，若 IQ4_XS 无收益，不改主部署。

### 02｜Qwen4Exp CUDA HC gate 算子融合

**来源/日期**：[PR #30602](https://github.com/ggml-org/llama.cpp/pull/30602)，本周合并（10-17～23）。**结论**：将 SCALE→SIGMOID→SCALE→hc_post 四步合为一个 CUDA kernel，减少 launch/中间张量。**开发者实测**：RTX PRO 6000 + Qwen4-Next，decode 约 +3%；缺少 GB10/4070 同机数字。**适用/限制**：仅 Qwen4Exp 相关模型路径，既有 dense Qwen3.8-27B 未必触发。**复现**：合并前后同一 Qwen4Exp GGUF，c8192/32768、pp512/2048、tg128/512、-fa 1、并发1/2；Nsight 看 kernel 数与时间，另测端到端、VRAM、输出一致性。**建议 P1 GB10**，不直接部署到当前 dense 基线。

### 03｜CUDA 分组专家 top-k fusion

**来源/日期**：[PR #29181](https://github.com/ggml-org/llama.cpp/pull/29181)，本周合并。**结论**：分组 MoE 的专家选择可融合，避免分组引入的额外开销。**开发者实测**：BailingMoE2 16B-A1B Q8_0，tg128 359.26→432.82 tok/s（1.20×），tg512 357.53→430.90（1.20×）；原 PR 未给可直接泛化到 Qwen3.8/GB10 的数值。**适用/限制**：需模型确实使用 grouped expert routing；dense 不适用，16GB 下 Q8_0 权重是否能装入须先核算。**复现**：相同 grouped-MoE GGUF、同采样、-p512 -n128/512 -ngl999 -fa1，A/B commit、核对输出/路由、GPU profiler 与显存。**建议 P1 GB10**。

### 04｜llama-server SWA checkpoint 失效逻辑修复

**来源/日期**：[PR #30666](https://github.com/ggml-org/llama.cpp/pull/30666)，10-19 合并。**结论**：修复从无关 prompt 恢复过期 SWA checkpoint 的问题，属于多会话状态正确性，而非提速。**开发者验证**：新增修复前失败、修复后通过的 A/B 回归测试；**没有吞吐加速数字**。**适用/限制**：使用 sliding-window attention、slot 恢复、多轮/多用户时相关；普通单次 dense prompt 价值有限。**复现**：构造 A/B 两个不共享前缀的提示，交替使用 slot、save/restore，比较旧新 commit 与无缓存基准输出，记录污染率、hash、TTFT、RSS、VRAM。**建议 P0**：server 稳定性优先，防止缓存错用。

### 05｜Responses API SSE 并行工具调用修复

**来源/日期**：[PR #30863](https://github.com/ggml-org/llama.cpp/pull/30863)，10-20 合并。**结论**：流式 SSE 增加 output_index、content_index，按工具索引维护 function-call item ID，防止并行工具的参数 delta 错配。**开发者验证**：Qwen3.8 27B 的并行工具调用可以正确关联；无性能数字。**适用/限制**：主要是 /v1/responses，不能推断 Spring AI 1.1.0 的 /v1/chat/completions 分片问题已修复。**复现**：构造 2～3 个同时触发的工具，混合无参/有参；保存原始 SSE 并按 item id、output_index、tool name、arguments 重组，对照非流式正确性；并发1/4/8，记录解析失败率、TTFT、p95。**建议 P0 Agent**，尤其适合本地编码 Agent 网关回归。

### 06｜Qwen-VL 图像 resize 与 Transformers 对齐

**来源/日期**：[PR #30736](https://github.com/ggml-org/llama.cpp/pull/30736)，本周合并。**结论**：修正 letterbox 黑边与 Python half-even rounding 差异；既有 GGUF 无需重新量化。**开发者实测**：Qwen3.5-2B 对 768×400 图片，图像 token 312→288，与 Transformers 的 288 一致；640×240 OCR 样例旧版识别“fs”，新版识别“4729”；某 640×240 图片最差 token embedding cosine 0.0367→0.9982（CPU/F16 mmproj 对照）。**适用/限制**：4070、GB10、Mac 均可做图像一致性回归；这是准确率修复，不保证更快。**复现**：使用 Qwen3.5-2B GGUF + F16 mmproj，固定 640×240、768×400、400×400 三张测试图，运行 llama-mtmd-cli -hf unsloth/Qwen3.5-2B-GGUF:Q4_K_M --image img.png -p "What is written in this image? Reply with just the text." --temp 0；旧新版本比较 token 数、OCR、图片 embedding、pp/VRAM。**建议 P0 4070**。

### 07｜MLX GLM-DSA 稀疏 prefill：长上下文收益

**来源/日期**：[ml-explore/mlx-lm PR #1997](https://github.com/ml-explore/mlx-lm/pull/1997)，10-23 合并。**结论**：缓存超过默认 16,384 tokens 后，GLM-DSA prefill 从密集扫描历史 KV 改为 gather indexer 选中的 top-k，索引分块处理，理论每块从 O(L×N) 转为 O(L×topk)；decode 路径不变。**开发者实测**：M3 Ultra 512GB、MLX 0.32.3、GLM-5.3-4bit，pp512@32K 42.4→128.0 tok/s（3.02×），@64K 22.4→114.8（5.12×），@128K 11.5→96.0（8.33×）；mlx_lm.benchmark @32K 87.3→159.3（1.82×），@64K 51.6→142.2（2.76×）。**限制**：只适用相应 GLM-DSA 实现；这些不是 64/128GB Mac 或 GB10 的数字。**复现**：基线 commit 与合并后，MLX 0.32.3、同 4bit 模型，python -m mlx_lm.benchmark --model mlx-community/GLM-5.3-4bit --prompt-tokens 32768 --generation-tokens 128 --num-trials 3；重复 65536，记录 pp、tg、统一内存峰值、TTFT、正确性。**建议 P1 Mac**，不套用到 llama.cpp。

### 08｜ComfyUI Dynamic VRAM KV：图像编辑跨 VRAM/RAM

**来源/日期**：[ComfyUI PR #17274](https://github.com/Comfy-Org/ComfyUI/pull/17274)，10-22 合并，包含 Aimdo 0.6.0。**结论**：把 Qwen-Image 2.1 KV cache 作为可动态 offload 的独立资源，在 VRAM 边界附近减少性能陡降；长期持久化和 Qwen3.x 全面支持是后续阶段。**开发者实测**：Windows RTX 3060 + 16GB RAM，1536px 参考图→768px 输出、25 steps，单次 prompt 72.97→44.05 秒；采样段 57→27 秒。**限制**：未给峰值 VRAM 精确 MiB、卡的具体显存版本和质量基准；不能直接推断 4070 Ti Super 同倍率。**复现**：固定 Qwen-Image 2.1 模型 SHA、参考图 1536px、输出 768px、25 steps、CFG、seed，ComfyUI 合并前后同机 A/B，nvidia-smi 100ms 采样 VRAM、RSS、PCIe、端到端墙钟、生成图差异和 OOM。再测试 1024px，记录失败。**建议 P0 4070**，仅隔离环境测试。

### 09｜ComfyUI Qwen 自适应树形 MTP

**来源/日期**：[PR #17273](https://github.com/Comfy-Org/ComfyUI/pull/17273)，10-22 合并；同时更新 comfy-kitchen 0.2.40。**结论**：draft 深度与 sibling 广度可根据输入动态选择，而非固定单一路径；是 ComfyUI 的 Qwen 文本生成实现，不是 llama.cpp 原生 MTP。**开发者实测**：Linux RTX 5090、Qwen3.8 W4A8，1536px 图像输入/4096 token：105.54→120.90 tok/s（约 1.15×），总时间 38.44→35.16 秒；另一个 Qwen3.5 W6A8 文本 209.26→250.68 tok/s。**限制**：本次 PR 还滚动更新 comfy-kitchen，不能将全部收益单独归因于树形策略；16GB 上模型权重与 KV 很可能受限。**复现**：GB10 使用兼容 ComfyUI 环境，固定 Qwen W4A8、图像、prompt、输出 token、采样，固定 MTP 与 adaptive-tree 两模式对照；记录接受率、实际 token/s、TTFT、VRAM、错误率。**建议 P1 GB10**。

### 10｜ComfyUI 原生 Fibo 2.0 图像生成/编辑

**来源/日期**：[PR #17240](https://github.com/Comfy-Org/ComfyUI/pull/17240)，10-21 合并；[模型卡](https://huggingface.co/Comfy-Org/Fibo-2.0)。**结论**：支持 Fibo 2.0 Dev 文生图与 Edit Turbo 图像编辑，文本编码器使用 Qwen3-VL-4B、FLUX.2 VAE；Edit Turbo 建议 4 steps/CFG1，Dev 30 steps/CFG5，不可混用参数。**开发者验证**：与 Diffusers 参考实现做 fp32/bf16 数值一致性测试，编辑案例约 49.8 dB PSNR；**未提供 4070/GB10/Mac 的峰值显存和每图耗时**。**硬件/限制**：4070 16GB 应先测试 INT8/offload；模型卡许可需单独核查，不因代码开源推定权重可商用。**复现**：ComfyUI 官方 Fibo 2.0 工作流，固定 seed，512²/768²/1024²、Turbo 4 steps 与 Dev 30 steps 分开跑，记录单图秒数、峰值 VRAM/RAM、成功率、质量/文字渲染、首图加载时间。**建议 P1**。

### 11｜MOSS-Image Edit LoRA：参考 KV 跨 step 复用

**来源/日期**：[ComfyUI PR #17296](https://github.com/Comfy-Org/ComfyUI/pull/17296)，10-22 合并；[LoRA](https://huggingface.co/chinoll/Moss-Image-Edit)。**结论**：为 MOSS-Image Edit 的参考图引入 reference_latents 与 RoPE 布局，隔离布局下参考图 K/V 只计算一次，不再每 step 重算。**开发者实测**：1024×1024 输出 + 1MP 参考图，826→457 ms/step（约 1.81× step 速度）；**没有给出单张总生成秒数和显存峰值**。**硬件/限制**：4070 CUDA 优先，需正确 LoRA、模型和显存预算；Mac 节点兼容待验证。**复现**：同 LoRA/seed、1024²/1MP reference、steps 8/20、原始与缓存路径；记录 ms/step、单图墙钟、VRAM/RAM、参考一致性、OOM、输出差异。**建议 P1 4070**。

### 12｜Diffusers LTX-2.5 视频 motion_speed 控制

**来源/日期**：[Diffusers PR #14967](https://github.com/huggingface/diffusers/pull/14967)，本周合并；[官方 LoRA](https://huggingface.co/Lightricks/LTX-2.5-22b-LoRA-Slow-Motion-Control)。**结论**：将视频播放 frame_rate 与模型运动条件 motion_speed 分离；motion_speed=0.2 对应训练过的 5× slow motion，默认 1.0 保持旧行为。避免直接修改 fps 导致音频长度/视频时长一起改变。**开发者验证**：回归测试证明 motion_speed 改变时间位置条件而不改变音频长度/输出 shape；**没有本周同机视频生成时长或显存基准**。**硬件/限制**：22B 视频模型的完整精度及参考流程不应假定能在 16GB 直接运行；GB10 128GB 更适合做第一轮可行性测试，Mac 兼容待查。**复现**：同 checkpoint/LoRA、121 frames、24 fps、motion_speed 1.0/0.5/0.2、同 prompt/seed/steps，记录内容时长约 5.04s、真实生成墙钟、峰值显存/RAM、分辨率、帧数、音视频同步与动作变化；视频 5 秒绝非 5 秒生成。**建议 P2 GB10**。

### 4.1 RTX 4070 Ti Super：CUDA 版本 A/B

~~~
# 先保存旧二进制/commit，不覆盖正在运行的服务
git clone https://github.com/ggml-org/llama.cpp.git llama-20261023

cmake -S . -B build-base -DGGML_CUDA=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build-base -j 8
git checkout 2744e48
cmake -S . -B build-pr -DGGML_CUDA=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build-pr -j 8
./build-base/bin/llama-bench -m /models/Qwen3.5-9B-Q3_K_S.gguf -ngl 999 -fa 1 -p 256 -n 128 -ub 4 -r 3
./build-pr/bin/llama-bench -m /models/Qwen3.5-9B-Q3_K_S.gguf -ngl 999 -fa 1 -p 256 -n 128 -ub 4 -r 3
~~~

模型路径为示例；PR commit 2744e48 为 10-17 合并节点，先确认 git log 与命令 --help。另用现有 IQ4_XS 27B、c6144/7168、KV q8_0、-fa on、-b2048 做实际服务回归。**先测 OOM 与正确性，再比较 pp/tg**。不同 GGUF 不能计算跨模型加速比。

### 4.2 Server/VLM 正确性与并发

~~~
# 选已包含 10-20 修复的固定 llama.cpp commit；显式端口避免默认端口变化
./build/bin/llama-server -m /models/Qwen3.8-27B-IQ4_XS.gguf \
  -ngl 999 -c 6144 -fa on -b 2048 \
  --cache-type-k q8_0 --cache-type-v q8_0 --host 127.0.0.1 --port 8081
# SSE 原始事件可由 curl -N 保存；必须使用支持 Responses API 的请求 JSON
curl -N http://127.0.0.1:8081/v1/responses \
  -H 'Content-Type: application/json' -d @responses-tools.json > events.sse
~~~

responses-tools.json 应包含 2 个可并行执行、名字/参数不同的工具；按实际 schema 编写。对比非流式及旧版，记录 tool_call_id/索引/参数拼接、失败率、TTFT/p95、slot 交替污染。VLM 使用第 06 项命令，记录 OCR 准确率和 image tokens。建议至少 3 次重复；同机不同进程顺序交替，避免热缓存偏差。

### 4.3 Mac MLX 与生成模型

### 4.4 统一指标

## 五、相对上期的增量与缺口

## 六、下周最值得复现的 3 个实验

1. **P0｜4070 CUDA MMVQ 量化矩阵**：9B Q2_K/Q3_K_S A/B、27B IQ4_XS 对照，-ub 1/2/4/512、p256/2048、tg128/256。**预期**：明确 4070 上是否存在低比特收益，且防止把 3090 的 1.56×误套到 4070。**风险**：16GB OOM、量化精度、内核收益只在特定 batch。
2. **P0｜4070 Qwen-VL 预处理 + Agent SSE 回归**：640×240、768×400 OCR；2～3 个并行工具的原始 SSE；slot A/B。**预期**：消除图片 token 差异与并行工具参数错配。**风险**：不同 endpoint/客户端实现差异，不能直接推断 Spring AI 已修复。
3. **P0/P1｜4070 ComfyUI Dynamic VRAM KV 与 MOSS 编辑**：Qwen-Image 2.1 1536px 参考→768px 25 steps，MOSS 1024²/1MP reference；固定 seed、测单图秒数与 VRAM。**预期**：验证 VRAM 边界性能和参考 KV 复用收益。**风险**：offload 反而变慢、依赖冲突、权重许可证和峰值内存。

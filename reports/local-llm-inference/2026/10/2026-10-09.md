# 本地 LLM 推理研究深度简报｜2026-10-09

> 统计窗口：2026-10-02～10-09（北京时间）；本专题首期。A=官方代码/公告，B=论文作者实验，C=第三方可核查单机实验，D=待测推测。P0=建议优先动手，P1=准备后验证，P2=研究储备。**本文没有在用户硬件上运行任何实验；下列命令是建议方案。**

## 一、本期摘要

本周值得优先验证的是 llama.cpp v0.6.0 在 RTX 4070 Ti Super 16GB 上的回归表现，以及 Qwen4Exp 的 MTP 推测解码在 DGX Spark / GB10 上的真实接受率。Apple Silicon 的 Metal 内核出现新优化，但算子加速不能直接换算成整机生成速度。两篇 KV cache 论文提出新的淘汰策略，尚无可直接在现有 llama.cpp 中启用的证据。视觉方向有 EmbeddingGemma 2 的本地跨模态检索进展；图片/视频生成本周缺少满足严格可复现要求的新硬件实测，不编造数据。

**历史硬件基线（非本周实测）**：RTX 4070 Ti Super 16GB + Ubuntu 22.04，Qwen3.8-27B-IQ4_XS GGUF，-ngl 999、-c 6144～7168、-fa on、-b 2048、K/V q8_0；pp 约 228～240 tok/s、tg 约 34.1～34.5 tok/s、显存约 14,750 MiB，8192 context 曾 OOM。另一平台为 DGX Spark / GB10 128GB，Mac Apple Silicon 作为对照平台；不虚构后两者的用户实测。

## 三、重点研究与落地分析

### 01. llama.cpp v0.6.0：先测兼容性，再看性能

**来源**：[官方 v0.6.0](https://github.com/ggml-org/llama.cpp/releases/tag/v0.6.0)，2026-10-05，commit d812350。新增 llama_batch_ext / llama_process 混合 token/embedding API、ggml v0.26.0、server 多模态 embedding 与模型模态元信息、CUDA W4A4（NVFP4/MXFP4）路径、KV 恢复修复；session/state 格式升至 11/4。**适用**：16GB、GB10、Mac；4070 Ti Super 不应默认享有 NVFP4 特殊路径的加速。**复现**：同一 GGUF，旧版与 v0.6.0，c=6144/7168、pp512/2048、tg128/256、并发 1/2 各三次，测 pp/tg、TTFT、p95、VRAM、OOM、回答正确率。**结果**：无本周同机新测；历史 tg 34.1～34.5 仅为旧基线。**P0**：并行测试，确认兼容后再替换服务。

### 02. CUDA TOP_K：局部热点改善不等于整体 6×

**来源**：[b11513 官方预发布](https://github.com/ggml-org/llama.cpp/releases/tag/b11513)，2026-10-08；[PR #28713](https://github.com/ggml-org/llama.cpp/pull/28713)。按 TOP_K 行数和行宽选择 bitonic、radix、DeviceTopK/CUB。**作者微基准**：Qwen4Exp、34,816 tokens，TOP_K 从 1,671,253 次 launch / 5,761.8ms 降到 2,329 次 / 941.8ms，约 6.1× **TOP_K 局部耗时改善**；并非 decode 全链路 6.1×。**适用**：NVIDIA、Qwen4Exp 稀疏索引；普通 Qwen3.8-27B 收益未知。**复现**：v0.6.0 vs b11513，同 GGUF、KV 深度 0/8K/32K（工具支持时），Nsight 统计 TOP_K kernel 与实际 tg128、显存、质量。**P1**。

### 03. Qwen4Exp MTP：GB10 推测解码

**来源**：[llama.cpp v0.6.0](https://github.com/ggml-org/llama.cpp/releases/tag/v0.6.0)，2026-10-05；[MTP PR](https://github.com/ggml-org/llama.cpp/pull/29761)。官方报告 DGX Spark decode 约 **1.5×**。**旧第三方实测（非本周新增）**：[单台 GB10 sweep](https://github.com/Weschera/Qwen3.8-Flash-Next-1x-DGX-Spark)，2026-09-02，特定代码任务 off 约 24.5 tok/s、draft-n=4 约 47.1 tok/s；不能把该负载的结果当成普适收益。**适用**：GB10 优先；需兼容 Qwen4Exp GGUF 与 MTP 草稿头，权重+KV 不宜直接搬到 16GB。**复现**：MTP off、draft-n=3/4/5，c8192，代码/普通文本/推理三类各三次，测接受率、tg、TTFT、峰值统一内存、正确率；低接受率可能更慢。**P0（GB10）**。

### 04. Apple Metal few-row MMA / FlashAttention

**来源**：[v0.6.0](https://github.com/ggml-org/llama.cpp/releases/tag/v0.6.0)，2026-10-05；[MMA PR](https://github.com/ggml-org/llama.cpp/pull/29869)、[FA PR](https://github.com/ggml-org/llama.cpp/pull/29570)。官方称部分 speculative/batched matmul 最高约 **3×**，另有 F16 KV 的 Metal tensor-API flash attention；**非整机生成 3×**。**适用**：Apple GPU，CUDA/GB10 不适用。**复现**：Mac 上固定 8B/27B GGUF，v0.5.0 vs v0.6.0，单流和并发 2/4，F16/q8_0 KV 分开测 pp/tg、aggregate tok/s、p95、内存。**结果**：无用户 Mac 新测。**P1**。

### 05. Behavior-Preserving KV Compression

**来源**：[arXiv:2610.06479](https://arxiv.org/abs/2610.06479)，2026-10-05。根据删除 KV 对 next-token logits 分布的 KL 影响选择保留项，不只看 attention mass；评分也有计算成本。**作者实验**：Qwen3-8B、LongBench、淘汰 90% KV 时本文方法 **41.6**、SnapKV **32.2**、full KV **48.9**（质量分数，不是吞吐）。**适用**：KV 主导的长上下文；不是 llama.cpp 的 -ctk/-ctv 开关。**复现协议**：full/SnapKV/本文方法，8K/16K、保留率 10/25/50%，测 LongBench/RULER、峰值显存、TTFT、tg、评分开销；未确认即装即用的官方 llama.cpp 实现。**P1，研究验证**。

### 06. DeferKV：推迟淘汰至首个真实 decode step

**来源**：[arXiv:2610.06286](https://arxiv.org/abs/2610.06286)，2026-10-05。利用第一步真实生成的 attention 信号再决定淘汰，减少 prefill 结束时的误判；无需训练/草稿模型。**作者报告**：LongBench、RULER、Needle-in-a-Haystack 质量改善，但摘要缺少可统一比较的吞吐/显存数值。**适用**：长提示问答；首步暂留完整 KV 可能让 16GB 设备 OOM。**复现协议**：prefill-end vs first-decode eviction，8K/16K、保留率 25/50%，测首步 VRAM、TTFT、tg、RULER/Needle 正确率；没有可直接使用的 llama.cpp CLI 开关。**P1**。

### 07. Agent 持久记忆：消融中未检出额外收益

**来源**：[arXiv:2610.07782](https://arxiv.org/abs/2610.07782)，2026-10-06。**作者实验**：分解 Agent 峰值 KV working set **14.3 MiB/请求**，单次 **35.5 MiB**，RAG **35.3 MiB**；加持久记忆正确率变化 **+0.015，95% CI [-0.011,+0.046]**，未检出可靠收益。数字仅限该论文小规模负载，不是通用模型 KV 需求。**适用**：本地 Agent 编排与消融评测。**复现协议**：single-pass、RAG、分解 Agent、Agent+memory 四组，各 ≥100 问，测总 token、总耗时、KV 峰值、正确率/置信区间、跨任务泄漏。**P2**。

### 08. ServeTwin：闭环服务模拟

**来源**：[arXiv:2610.02732](https://arxiv.org/abs/2610.02732)，2026-10-02。模拟 ragged batch、CUDA graph padding、请求队列、KV 状态和 prefill/decode 分离。**作者实验**：重现 InferenceX 稳态吞吐-交互曲线平均误差 **3.6%**，LMBenchmark 多轮预测误差 **9.9%**；这些是模拟误差，不是加速幅度。**适用**：多卡/大并发容量规划，单张 16GB 应先真实压测。**复现协议**：并发 1/2/4/8、输入 512/2048/4096、输出 128/256，先测 QPS、p50/p95、总 tok/s、VRAM，再与模拟预测比较；可运行官方实现尚需核实。**P2**。

### 09. EmbeddingGemma 2：本地图文音视频统一检索

**来源**：[Google 公告](https://developers.googleblog.com/en/google-ai-edge-with-embeddinggemma-2/)，2026-10-06；[模型卡](https://huggingface.co/google/embeddinggemma-2)；[GGUF](https://huggingface.co/ggml-org/embeddinggemma-2-GGUF)。Apache-2.0，740M 总参数；文本 270M、图文 440M，文本/图片/视频帧/音频统一 768 维，支持 512/256/128 维截断，8K 共享上下文。**官方质量指标**：Code MTEB **78.68 vs 前代 68.76**，不是速度。**适用**：16GB、GB10、Mac；模型卡警告 **FP16 可能 NaN，建议 BF16/FP32**。**复现**：100 图/20 查询，原生 text→image vs caption→text embedding，768 vs 256 维，测 Recall@5、p50/p95 编码时延、峰值内存、索引体积；本周无同机速度。**P0**。这是检索模型，不是图片/视频生成。

### 10. Ollama v0.40.2：模型升级与磁盘备份

**来源**：[官方 v0.40.2](https://github.com/ollama/ollama/releases/tag/v0.40.2)，2026-10-08；[v0.40.1](https://github.com/ollama/ollama/releases/tag/v0.40.1)，10-07。旧版下载模型首次运行时可能后台升级以改善 llama.cpp 兼容；为支持降级暂留原副本，**磁盘占用可能暂时增加**；修复列表重复。Apple Silicon 默认 MLX 对受支持架构的切换属于 09-25 v0.40.0，**不是本周新功能**。**复现**：升级前后记录 ollama list、df -h、同 prompt 的 total_duration/eval_count/eval_duration、RAM/VRAM、Mac 实际 MLX 后端。无官方同机端到端提速百分比。**P1**。

## 四、通用复现命令与统一评价口径

以下在 RTX 4070 Ti Super Ubuntu/CUDA 环境使用；模型路径需替换。GB10 使用本机 ARM64 CUDA 构建，Mac 使用 Metal 构建而不是 CUDA。

~~~bash
git clone https://github.com/ggml-org/llama.cpp.git
cd llama.cpp
git checkout v0.6.0
cmake -S . -B build -DGGML_CUDA=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build -j 8
./build/bin/llama-bench -m /models/Qwen3.8-27B-IQ4_XS.gguf -ngl 999 -p 512 -n 128 -r 3 -fa 1
./build/bin/llama-server -m /models/Qwen3.8-27B-IQ4_XS.gguf -ngl 999 -c 6144 -fa on -b 2048 -ub 512 --cache-type-k q8_0 --cache-type-v q8_0 --host 127.0.0.1 --port 8080
nvidia-smi
~~~

Qwen4Exp MTP 在权重和草稿头匹配且内存足够时可测试：

~~~bash
./build/bin/llama-server -m /models/Qwen3.8-Flash-Next-Q4.gguf -md /models/mtp-Qwen3.8-Flash-Next-Q8_0.gguf --spec-type draft-mtp --spec-draft-n-max 4 -ngl 999 -c 8192 -fa on --host 127.0.0.1 --port 8893
~~~

EmbeddingGemma 2 的纯文本接口可作为加载检查（新架构需要近期 Transformers/SentenceTransformers）：

~~~python
import torch, time
from sentence_transformers import SentenceTransformer
m = SentenceTransformer("google/embeddinggemma-2", model_kwargs={"torch_dtype": torch.bfloat16})
t = time.perf_counter()
v = m.encode(["How to optimize CUDA KV cache?"], prompt_name="SearchQuery",
             truncate_dim=256, normalize_embeddings=True)
print(v.shape, time.perf_counter() - t)
~~~

**公平比较**：同一 GGUF SHA256、prompt/tokenizer、采样参数、驱动/CUDA、commit、batch/ubatch、KV 类型，先热身，重复 ≥3 次；分开记录 pp/tg、单流/总吞吐、TTFT、p50/p95、峰值显存、OOM、准确率。论文算法没有开放实现时只能做对照设计，不应声称已复现。

## 六、最值得复现的三个实验

**实验 A｜4070 Ti Super v0.6.0 A/B（P0，约半天）**：旧版 vs v0.6.0，固定 27B IQ4_XS、c6144/7168、KV q8_0、-fa on；pp512/2048、tg128/256、并发 1/2，各 ≥3 次。指标为 pp/tg、TTFT、p95、VRAM、OOM、正确率；稳定后再试 c8192。**预期收益**：可能有 CUDA/显存管理改进，但幅度未知。**风险**：内核回归、旧 session 兼容、8192 OOM。

**实验 B｜GB10 Qwen4Exp MTP（P0，0.5～1 天，不含下载）**：MTP off/draft-n=3/4/5，代码/普通文本/长推理三类 prompt，c8192/32768（内存允许才测），各 ≥3 次。指标为接受率、tg、TTFT、峰值统一内存、质量与长上下文衰减。**预期收益**：高接受率代码任务可能提速。**风险**：权重+草稿头占内存、低接受率变慢；历史第三方 47 tok/s 不是本机承诺。

**实验 C｜EmbeddingGemma 2 图文检索（P0，约半天）**：100 图/20 查询，BF16，原生 text→image 与 caption→text embedding 对照；768 vs 256 维。指标为 Recall@5、编码 p50/p95、VRAM、索引体积、中文查询质量。**预期收益**：可能简化多模型链路；**风险**：新架构库兼容、维度截断质量损失、FP16 数值异常。

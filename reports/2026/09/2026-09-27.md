## 1. 本周摘要

本周最值得关注的变化集中在 **Spring AI 2.1、MCP Skills、Codex Desktop 稳定性** 三条线上。

- **Spring AI 2.1.0-M1** 于 9 月 25 日发布，新增 OpenAI Responses API、`MessagePart`、`VectorStore.upsert` 等能力，并升级到 Spring Boot 4.2。官方同时明确 Spring AI Agents 后续路线：计划 2026 年 11 月以 Spring Projects Experimental 独立项目发布，并计划在 2027 年中并入 Spring AI 3.0。
- **Spring AI Session / MessagePart** 值得重点关注。未来 SessionRepository 将面向完整 MessagePart 持久化，包括 reasoning 等内容，这会影响后续 provider mapping、conversation persistence 和 reasoning 恢复链路的设计。
- **MCP 2026-07-28**：Spring 官方已明确确认，新协议支持正在 MCP Java SDK 与 Spring AI MCP abstractions / annotations 两层推进。
- **MCP Skills**：MCP 组织维护的 Skills 扩展已形成稳定规范，定义 `skills/list`、`skills/get` 等接口，为远程 Skill discovery / progressive disclosure 提供协议层基础。
- **Codex**：9 月 25～26 日 Windows/Linux Desktop 出现多条 401、启动卡住、thread 无法恢复等 issue。本周更适合观察稳定性，而不是主动追桌面端最新版本。
- **Qwen / llama.cpp**：本周没有新的 Qwen 主模型发布；llama.cpp 继续高频迭代，但没有发现足以建议现有 CUDA + Qwen3.8-27B 环境立即重跑 benchmark 的重大变化。

### 2.2 Spring AI Session：reasoning 持久化链路值得提前关注

**标签**：`Spring AI` `Reasoning` `Session`  
**重要性**：高

Spring AI 2.1 路线中，Session 能力将逐渐覆盖：

- conversation history
- compaction
- recall
- MessagePart persistence

这意味着 reasoning 等内容未来可能不只是一次模型响应中的临时 metadata，而可能进入完整 conversation persistence。

对于 OpenAI-compatible 网关下 reasoning / reasoning_content 的适配，未来排查链路可能演变为：

```text
wire response
  ↓
provider DTO / deserialization
  ↓
MessagePart
  ↓
AssistantMessage / Session
  ↓
SessionRepository
  ↓
下一轮 conversation restore
```

因此，自定义统一适配层不宜长期锁死在 `AssistantMessage.metadata`。

### 2.4 MCP Skills：Skill discovery 进入协议层

**标签**：`MCP` `Skills` `Progressive Disclosure`  
**重要性**：高

MCP Skills 扩展已经形成稳定规范，核心接口包括：

- `skills/list`
- `skills/get`
- 可选 `resources/directory/read`

Skill 文件可以映射为 `skill://...` resources，并支持 manifest / digest。

这使得 Agent 的渐进式能力加载可以进一步拆成：

```text
任务
 ↓
Skill Discovery
 ↓
加载 SKILL.md / resources
 ↓
Tool Search
 ↓
动态加入少量 Tool
 ↓
Tool Execution
```

因此 MCP Skills 与 Spring AI `ToolSearchToolCallingAdvisor` 并不是互斥方案。

前者更偏向：

> 能力/知识/流程的发现与渐进加载

后者更偏向：

> 大量 Tool 中检索当前需要暴露给模型的 Tool

两者组合后，比单纯 Tool Search 更接近完整 Agent Runtime。

安全方面需要特别注意：远程 Skill 内容应作为不可信模型输入，Skill 内的文本指令不应该隐式获得本地执行权限。

这也可以延伸到 MCP 权限模型：

```text
Tool Path Authorization
+
Skill Path / Skill Origin Authorization
```

来源：
- https://github.com/modelcontextprotocol/ext-skills
- https://github.com/modelcontextprotocol/ext-skills/blob/main/specification/stable/skills.mdx

## 4. 关键技术细节

### 4.1 MessagePart 可能成为 reasoning 统一表达的重要基础

第三方 OpenAI-compatible 模型经常存在：

- `reasoning`
- `reasoning_content`
- tool calls
- provider-specific content

映射位置不统一的问题。

MessagePart 的方向是把不同类型的 message content 变成结构化的一等表达。

因此，对于未来自定义适配层，更值得参考：

```text
Provider Response
      ↓
Provider-specific DTO
      ↓
Normalized MessagePart
      ↓
AssistantMessage / Session
```

而不是长期把所有扩展字段塞入 metadata。

### 4.2 Skill Discovery ≠ Tool Retrieval ≠ Tool Execution

三层应明确区分：

```text
Skill Discovery
      ↓
Tool Retrieval
      ↓
Tool Execution
```

一种值得实验的 Java Agent 架构是：

```text
Agent Runtime
├── MCP Skills
│   └── progressive knowledge / workflow loading
├── Tool Search
│   ├── Lucene
│   └── JEV
├── Dynamic Tool Context
├── MCP / Function Calling
├── Memory / Session
└── Planner
```

这也意味着 JEV × Spring AI 实验可以从单纯比较 Retrieval 算法，进一步扩展到完整 progressive capability loading。

## 5. 对现有技术方案可能产生的影响

### Spring AI 1.1.x

当前生产/现有排障项目无需因为本周变化升级。

reasoning 映射问题仍应基于：

- 实际运行时 JAR
- 实际 OpenAI-compatible response
- Jackson / DTO 反序列化
- ChatCompletionChunk
- AssistantMessage mapping

进行定位。

### Spring AI 2.x

建议建立独立 2.1.0-M1 PoC，不直接替换 2.0.1 主项目。

优先实验：

1. Responses API
2. MessagePart
3. reasoning content
4. streaming/non-streaming
5. Tool Calling + MessagePart
6. Session persistence

### Jev × Spring AI Tool Loading

当前实验不需要推翻。

下一阶段可以扩展为：

```text
MCP Skills
   ↓
JEV / Lucene Tool Search
   ↓
Dynamic Tools
   ↓
MCP Tool Execution
```

这比单纯比较 JEV 与 Lucene 更接近真实 Agent Runtime。

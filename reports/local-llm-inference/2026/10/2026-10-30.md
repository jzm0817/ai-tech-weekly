# 本地 LLM 推理研究深度简报｜2026-10-30

> **第 4 期**。北京时间 2026-10-23 至 2026-10-30 18:00 的一周窗口。12 项独立变化；同一模型系列的相邻 PR 按不同机制区分，但不把它们当作独立端到端性能证明。**本期未在用户设备上执行任何基准。**文中“实测”仅指明确标注的上游开发者或第三方实验；没有实测的值统一为 NA。注意：本周部分项目于 10 月 30 日凌晨合并，报告以执行时已公开的记录为准。

## 一、执行摘要与硬件基线

**本周结论**：最值得关注的是 DGX Spark 上 Qwen3.8-Flash-Next 投机解码可能发生接受率回退的第三方复现、Metal MXFP4 单 token 优化、DeepSeek-V3.2 的 MLX 稀疏 prefill、MOSS 图像内存释放，以及 MiniMax-H3 的新 VAE 与 Pika H3 Flex 开放权重。**“新格式已合并”不等于 4070 Ti Super 上的现有 GGUF 自动提速**。ComfyUI 与 Pika 的本地视频功能已经有实质更新，但 16GB/GB10 的统一端到端视频生成数据仍不足。

**已有部署基线（历史记录，不是本周测试）**：Ubuntu 22.04 + RTX 4070 Ti Super 16GB，Qwen3.8-27B-IQ4_XS.gguf，-ngl 999、-c 6144/7168、-fa on、-b 2048、KV K/V q8_0；prompt processing 约 228–240 tok/s，decode 约 34.1–34.5 tok/s，显存约 14.75 GiB，8192 ctx 曾 OOM。DGX Spark/GB10 128GB：Ubuntu ARM64/CUDA 13.0；Mac Apple Silicon：仅评估兼容性，不假定用户拥有具体 Mac。不同模型/量化/平台不进行跨表“加速比”计算。

**证据边界**：A=上游已合并或开发者测试；C=第三方可核查但尚未独立交叉验证；D=待合并/待测。速度指标区分算子微秒、pp tok/s、tg tok/s、aggregate tok/s、TTFT、生成实际墙钟时间。所有推荐以不覆盖当前服务为前提。

## 三、逐项研究与实验建议

### 01｜ggml OCP FP8 E4M3：量化格式基础设施已合并

**来源/日期**：[llama.cpp PR #27512](https://github.com/ggml-org/llama.cpp/pull/27512)，2026-10-29 合并。**核心结论**：ggml 引入 OCP FP8 E4M3 饱和模式；这是格式和基础算子的铺垫，后续 CUDA、KV FP8、scale plumbing、Vulkan 由不同堆叠 PR 分别处理。不能因为本 PR merged 就认为 CUDA FP8 KV Cache、NVFP4 scale 和所有模型转换链已经稳定可用。**适用与限制**：4070 Ti Super、GB10 均需核对对应 CUDA backend 的合并状态与计算精度；现有 IQ4_XS 27B 不会因格式支持直接获益。**作者实测**：本 PR 未给 4070/GB10 端到端 pp/tg 或 FP8 KV 质量数据，NA。**复现**：固定 commit，先运行 test-backend-ops 与支持的 FP8 量化转换 smoke test；确认 CUDA PR #28413 和 KV PR #28392 的实际合并状态后才测试 K/V q8_0 与 FP8；比较 4096/7168 ctx、pp512/2048、tg128/256、VRAM、perplexity/问答准确率。**判断 P1**：先跟踪，暂不替换稳定 IQ4_XS 部署。

### 02｜CUDA 384 专家 TOPK_MOE：局部算子收益明显

**来源/日期**：[llama.cpp PR #31288](https://github.com/ggml-org/llama.cpp/pull/31288)，10-28 合并。**核心结论**：使既有 CUDA top-k MoE kernel 支持 DeepSeek-V4.1 的 384 experts，包含 1/8/22 tokens 测试。**开发者实测（A）**：RTX A6000、CUDA 13.0，router subgraph（包含 sqrt-softplus、bias、top6、归一化、缩放）1 token 从 23.91 µs 降至 4.78 µs，128 token 34.70→5.80 µs，512 token 76.82→6.60 µs；672/672 backend tests 通过。**尚无全模型吞吐或质量对比**。**硬件限制**：只有使用该 384 expert 路由的模型才触发；现有 dense Qwen3.8-27B 无收益。GB10 适合研究，4070 16GB 可能无法完整装入目标模型。**复现**：RTX/GB10 使用同 GGUF、PR 前 commit 8ca4060 vs 合并后 a7af149，先 test-backend-ops -o TOPK_MOE，再测 pp512/2048、tg128/512、GPU profiler、峰值显存和相同 prompt 的输出一致性。**判断 P1 GB10**：不把算子约 5×～12×当成模型 tok/s 提升。

### 03｜DGX Spark：Qwen3.8-Flash-Next speculative 接受率回退，根因未定

**来源/日期**：[llama.cpp issue #31220](https://github.com/ggml-org/llama.cpp/issues/31220)，10-26 提交、10-27/28 更新；仍标注 bug-unconfirmed。**核心结论**：第三方报告在 DGX Spark ARM64 上，Qwen3.8-Flash-Next + DFlash2/MTP 的草稿接受率随 CUDA softplus 数值实现改变而变化，导致投机收益回退；维护者在自己的 DGX Spark 未复现同一退化，**不能认定所有 Spark 均受影响或已确认根因**。**第三方实测（C）**：同 8 个 coding 请求，commit d327bf1→74bca39：平均输出 71.60→65.21 tok/s、接受率 0.6131→0.5623、平均延迟 16.225→17.938 s。另一轮新旧比较 DFlash2 69.75→64.33 tok/s，MTP 63.52→59.08；ngram-mod 30.47→31.26，方向相反。**硬件与限制**：GB10 128GB、CUDA13.0，Qwen3.8-Flash-Next 的 IQ4_NL、MTP/DFlash 草稿头；现有 4070 dense 27B 无法据此推断。**复现**：固定所有 GGUF SHA256、seed、-fa on、-ngl 999、-np 1、同 sampling；对比 d327bf1 与 74bca39，再用当前 master；--spec-type draft-dflash/draft-mtp/无草稿三组，每组至少 3 轮，运行 tools/server/bench/speed-bench/speed_bench.py --bench qualitative --category coding --osl 1024 --concurrency 1 --limit 8；记录接受率、pp/tg、E2E、TTFT、输出正确性。**判断 P0 GB10**：先测再升级；不要擅自修改 softplus 生产实现。

### 04｜Qwen3.6-35B-A3B：两张 8GB 卡承载 5 个 coding Agent

**来源/日期**：[llama.cpp discussion #31177](https://github.com/ggml-org/llama.cpp/discussions/31177)，10-26；第三方单机分享。**核心结论**：对 hybrid 模型按真正使用 attention KV 的层数而不是总层数计算 slot 容量，辅以 FIM 预热，可提高小卡并发密度。**第三方实测（C）**：两张 AMD BC-160 8GB（Vulkan），Qwen3.6-35B-A3B UD-IQ3_S，-c 163840 -np 5 -ngl 99 --n-cpu-moe 5 -fa on -ctk q8_0 -ctv q8_0 --cache-reuse 256 --ctx-checkpoints 4 --cache-ram 2048；作者称 KV 只在 40 层中的 10 层，5×32K slots；单请求约 38.5 tok/s、5 并发合计约 56 tok/s，FIM 中位延迟 1.57→1.0 s。**适用与限制**：GB10 可借鉴容量计算；4070 单 16GB 与两卡 Vulkan 并非同拓扑，数字不能移植。**复现**：GB10 上同一模型/量化（或清晰标注替代模型），-np 1/2/4/5、总 ctx 按 slot 分配，FIM warm-up on/off，记录每 slot KV+recurrent MiB、aggregate tok/s、TTFT/p95、RSS、OOM、正确率。**判断 P1**：优先作为多 Agent 容量设计参考，而非速度承诺。

### 05｜Metal MXFP4：Mac 上单 token decode 受益，模型差异显著

**来源/日期**：[llama.cpp PR #31075](https://github.com/ggml-org/llama.cpp/pull/31075)，10-29 合并。**核心结论**：MXFP4 mat-vec 改用 FP16 位技巧解码和对齐 nibble 读取，GLU/unary/binary 使用更多 threadgroups，减少单 token 的串行执行。**开发者实测（A）**：M3 Ultra、-fa 1 -p 512 -n 128 -r 3，Qwen3-4B MXFP4 tg128 131.7→154.4 tok/s（+17.3%），Qwen3.8-27B Q4_0 34.05→34.97（+2.7%），Qwen3.5-0.8B Q4_K_M 263.6→263.3（-0.1%）；pp512 变化 -0.2%～+0.5%。维护者额外测试 M5 Max 128GB 上 gpt-oss-20B tg128 150.89→150.75，几乎无收益。**适用与限制**：只针对 Apple Metal；不能类推 RTX CUDA 或所有量化格式。**复现**：M3/M5 同机、PR 前 8e5a58d vs 后 6d19453，模型 GGUF hash 固定，-fa 1 -p 512 -n 128 -r 5，另测 tg512、pp2048、统一内存峰值、温度/功耗、输出一致性。**判断 P1 Mac**：先选 MXFP4 模型；现有 4070 不适用。

### 06｜MLX DeepSeek-V3.2 稀疏 prefill：长上下文显著降内存

**来源/日期**：[mlx-lm PR #2013](https://github.com/ml-explore/mlx-lm/pull/2013)，10-28 合并。**核心结论**：将上周 GLM-DSA sparse prefill 机制移植到 DeepSeek-V3.2；缓存超过默认 16384 tokens 后，按 indexer top-k gather 选中 KV，4096 block 滚动 top-k，避免构建完整得分张量。**开发者实测（A）**：M3 Ultra 512GB、MLX 0.32.3、DeepSeek-V3.2-4bit，pp512@32K 40.9→84.6 tok/s（2.07×）、@64K 21.3→62.6（2.94×）、@128K 11.1→40.9（3.69×）；@128K pp512 峰值内存 425.5→395.7 GB；decode 基本 1.00×。**硬件限制**：模型约数百 GB，64/128GB Mac 不满足本实验容量；不能把 512GB 机器数据当作用户硬件可运行结论。**复现**：只在有 512GB 统一内存的 M3 Ultra 等适当设备，用同 4bit checkpoint，baseline vs merged，python -m mlx_lm.benchmark --model mlx-community/DeepSeek-V3.2-4bit --prompt-tokens 32768 --generation-tokens 128 --num-trials 3；再跑 65536，记录 pp、tg、峰值统一内存、质量/KLD、OOM。**判断 P1（大内存 Mac）**，4070/GB10 不可直接使用。

### 07｜MLX speculative logits_processor 历史修复

**来源/日期**：[mlx-lm PR #2014](https://github.com/ml-explore/mlx-lm/pull/2014)，10-27 合并。**核心结论**：投机解码时 repetition penalty 等 logits_processor 曾遗漏已有 prompt 历史，造成“有草稿”和“无草稿”输出不一致；修复处理器历史，并增加回归测试。**开发者验证（A）**：Qwen3-1.7B-4bit target、Qwen3-0.6B-4bit draft、repetition_penalty=1.3，修复后 draft 输出前缀与 no-draft 一致；未提供速度提升。**适用与限制**：Apple MLX，非 llama.cpp 的相同 bug 证明。**复现**：固定 seed、temp 0、同 prompt/processor，draft on/off、修复前后，比较 128/512 tokens exact match、重复率、接受率、TTFT、tok/s、内存。**判断 P1 Mac**：正确性优先，不能宣传为性能优化。

### 08｜MOSS-Image：提前释放中间张量以压低峰值显存

**来源/日期**：[ComfyUI PR #17338](https://github.com/Comfy-Org/ComfyUI/pull/17338)，10-25 合并。**核心结论**：在 MOSS 的 TextBlock.forward/Block.forward 计算后及时释放中间 tensor 引用，减少峰值生存期；注意这不是上期的 MOSS-Image Edit reference KV 缓存优化。**上游验证（A）**：代码已合并，但 PR 未提供可核实的峰值 MiB 或单图生成秒数，均 NA。**适用与限制**：4070 Ti Super 16GB 优先，是否有效取决于 PyTorch allocator、模型/分辨率/steps；GB10 也可测，Mac backend 未验证。**复现**：固定 ComfyUI 前后 commit、MOSS 权重 hash、1024×1024/768×768、seed 42、steps 8/20，记录 torch.cuda.max_memory_allocated、max_memory_reserved、nvidia-smi 峰值、RSS、单图墙钟、OOM、质量一致性；每组预热+3 次。**判断 P0 4070**：低风险验证，但不预设节省幅度。

### 09｜MiniMax Sol-H3-VAE：更快视频解码，但不同模型并非无损替换

**来源/日期**：[ComfyUI PR #17411](https://github.com/Comfy-Org/ComfyUI/pull/17411)，10-28 合并。**核心结论**：24 层蒸馏视频 VAE 解码器，以窗口注意力处理整段视频，替代原有 H3 VAE 的重叠时序块。**开发者实测（A）**：RTX 5090、1344×768×124 帧，H3 VAE fp16 10.7s / 5.5GiB 峰值；H3 VAE int8 4.61s / 3.2GiB；Sol fp16 3.28s / 5.9GiB；Sol int8 1.70s / 4.3GiB。Sol int8 比 H3 int8 解码快约 2.71×，**但峰值显存高 1.1GiB**；与原解码器约 39dB PSNR，非逐像素一致。**硬件限制**：GB10 优先；4070 16GB 即便 VAE 阶段能装入，也不代表完整 H3 生成链可运行；长片 activation 增长且不能 tile。**复现**：同一保存的 H3 latent，fp16/int8 原 VAE 与 Sol VAE 四组，固定 768p/124 帧，记录仅 VAE 解码墙钟、峰值显存、PSNR/SSIM、总流程耗时；不要把 1.70s 当作视频从 prompt 生成的耗时。**判断 P1 GB10**。

### 10｜MiniMax-H3 latent upscaler：16 帧时间块处理视频 latent

**来源/日期**：[ComfyUI PR #17412](https://github.com/Comfy-Org/ComfyUI/pull/17412)，10-28 合并；[upscaler 权重](https://huggingface.co/LBH-123-AI/Minimax_h3_latent_Upscaler)。**核心结论**：ComfyUI Load Latent Upscale Model 识别 H3 3D-conv 权重，MiniMaxH3LatentUpscaleWithModel 将视频 latent 放大到目标尺寸，16 帧 temporal slabs，clip-wide GroupNorm 统计，开发者称与单 pass 位级一致。**开发者验证（A）**：有实现和数值一致性描述；未公开 4070/GB10 的峰值显存、单视频超分墙钟、完整生成耗时，NA。**硬件限制**：GB10 先测；需要上游 H3 latent 与对应模型权重；不等于普通图片超分。**复现**：同一 H3 latent，原始解码与 latent upscaler→解码；目标 768p/1080p，帧数 24/124，记录 upscaler-only 和 pipeline 秒数、VRAM/RAM、PSNR/视觉差异、OOM；核对目标宽高与最终帧数。**判断 P1 GB10**。

### 11｜MiniMax-H3 context windows：长视频工作流接口新增

**来源/日期**：[ComfyUI PR #17425](https://github.com/Comfy-Org/ComfyUI/pull/17425)，10-30 合并。**核心结论**：为 MiniMax-H3 加入基本 context window 支持及更方便的节点；这是视频上下文窗口，不是 LLM 文本 KV cache 研究。**上游实测（A）**：代码合并，未提供统一分辨率、帧数、峰值显存、每段视频墙钟与连续性评分，均 NA。**硬件限制**：GB10 的长视频可能受益，但 128GB 统一内存不等于 128GB 高带宽独立显存；4070 16GB 未验证。**复现**：固定 H3 checkpoint、seed、steps、576p/768p、5s/10s，context windows on/off，记录切窗数量、生成墙钟、峰值内存、边界帧不连续率、音频同步、OOM；先确认模型权重许可。**判断 P2**：先做功能正确性，不承诺加速。

### 12｜Pika H3 Flex：六步开放权重视频+同步音频，硬件门槛需谨慎

**来源/日期**：[Pika 官方公告](https://creation.pika.art/blog/pika-h3-flex) 与 [官方推理仓库](https://github.com/Pika-Labs/Pika-H3-Flex)，10-29；[Diffusers PR #15150](https://github.com/huggingface/diffusers/pull/15150)，10-29 合并。**核心结论**：基于 MiniMax H3 的两组后训练 LoRA（FL2VA、Ref2VA），6 次去噪，支持 T2V/I2V/首尾帧/最多 12 个多模态参考；**本地原生 480p/768p、5～15 秒、24fps、32kHz 立体声**。1080p/2K/4K 放大、分离音轨属于托管 API，不是本地权重原生功能。**厂商声明与实测边界**：官方营销“15s 片段最快 7s”不是在 GB10/4070 上的完整生成墙钟。官方可下载推理包以单 H100 80GB 验证为主，完整基础组件下载约 210GB + adapters 5.5GB；**4070 16GB 和 GB10 ARM64 的可运行性、VRAM 峰值、真实每视频耗时均 NA**。CPU offload 不覆盖文本编码器和 VAE。**许可**：推理代码 Apache-2.0，adapter 权重受 MiniMax H3 Community License 限制，必须单独核对地域与商业使用。**复现**：仅在容量/依赖与许可核验后，先用单 H100 或受支持环境运行官方命令；GB10 仅做兼容性/内存预算预检，禁止宣称已支持。480p、16:9、5s、seed42、6 steps，记录 124 帧约 5.17s **内容时长**、单视频真实生成墙钟、VRAM/RAM、分阶段耗时、输出质量、音视频同步和失败原因。**判断 P1 研究、4070 P2**：优先读技术报告与确认低显存社区方案，而不是立即下载 215GB。

## 四、可复现实验脚本与评价规范

### 4.1 4070 Ti Super：保留既有稳定基线

~~~bash
# 两个独立目录构建，避免覆盖当前 llama-server
git clone https://github.com/ggml-org/llama.cpp.git llama-20261030
cd llama-20261030
git checkout a7af149^
cmake -S . -B build-before -DGGML_CUDA=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build-before -j 8
git checkout a7af149
cmake -S . -B build-after -DGGML_CUDA=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build-after -j 8
# 示例模型路径必须替换；只对支持的模型才测试 MoE kernel
./build-after/bin/test-backend-ops test -o TOPK_MOE -b CUDA0
~~~

## 六、下周最值得复现的三个实验

**实验 A｜P0：GB10 Qwen speculative 回归**。d327bf1、74bca39、当前固定 commit；同 Qwen3.8-Flash-Next IQ4_NL、draft DFlash2/MTP/无草稿，coding 8 条×3 次。**预期收益**：判断本机是否也存在 0.61→0.56 接受率回退，避免错误升级。**风险**：不同草稿权重、模板或随机性掩盖差异；根因未定，不改 CUDA 数学实现。

**实验 B｜P0：4070 MOSS 图像峰值显存 A/B**。ComfyUI #17338 前后、同 MOSS 权重、1024²、seed42、steps8/20，3 次。**预期收益**：确认是否减少 peak allocated/reserved、OOM、单图时间。**风险**：CUDA allocator 保留显存导致 nvidia-smi 不下降；需要同时记录 PyTorch 内部峰值。

**实验 C｜P1：GB10 MiniMax-H3 视频解码与超分分段测量**。先核实许可/ARM64/CUDA 支持，再使用**同一已有 latent**分别跑 H3 VAE int8 与 Sol-H3-VAE int8、latent upscaler on/off，124 帧 768p。**预期收益**：判断解码器 4.61→1.70s 的 RTX5090 局部优势是否可在 GB10 复现，并量化峰值内存代价。**风险**：完整生成链未必适配 GB10；解码速度不是完整视频生成速度；质量非逐像素一致。
